# Learning agents

Pi Durable owns conversations, transcripts, submission idempotency, execution recovery, model/tool runs and document transactions. Application code supplies subject policy, provider integration and HTTP delivery.

`server/agent.ts` is the shared Pi integration. It opens/closes the harness, connects the selected provider and registry, and translates Pi's live state into reply progress. `AgentDefinition` supplies a prompt, tool factory and execution budgets. Use a new stable ID for incompatible prompt/tool semantics. `language-agent.ts` owns language research, speech capabilities and the existing `runCoach` entry point. `math/agent.ts` supplies AoPS/IrMO teaching behavior. There is no separate agent facade or second execution engine.

`createStudy` in `server/learning/study.ts` supplies application rules around native Pi primitives:

- A persistent Pi conversation holds each study session's model transcript. Subsequent turns send the current question and learner state; Pi supplies prior conversation context and compacts it when needed.
- A Pi document holds the public session/profile and turn outcomes. A separate Pi index store maps public request IDs to sessions, preserving the app's subject-wide ownership checks beyond Pi's conversation-scoped request IDs.
- One Pi commit admits a submission and the pending application state. After schema validation, another commits the reply, learner and completed turn together.
- Retries reacquire the native submission. If a run ended unanswered, a native continuation retries it without duplicating the user message. A completed malformed response stays cached until the user discards it.
- Discard aborts unfinished work and atomically resets model context to accepted history while clearing the pending state. Invalid or discarded replies do not enter the next lesson's context.

Session methods are asynchronous. Each study session has its own Pi store at `study/<namespace>/<session-id>.sqlite` under the app data directory. This isolates recovery: Pi resumes all pending conversations in a harness, so another session must never supply its provider, prompt or request-bound tools. Per-session leases protect writers across processes while allowing unrelated sessions to run independently. Read-only harnesses let session/profile reads continue while a turn runs. The subject index has no runnable conversations and uses only short commits for session discovery and request ownership. Ownership is reserved before admission; the native submission and pending session state are then committed together in the session store. A reservation interrupted before admission is safe to retry with the same session, ID and message. Subject namespaces consist of lowercase ASCII letters/digits, start with a letter and have at most 40 characters. Treat each namespace and its profile schema as a permanent compatibility boundary.

On first access, existing subject SQL sessions/turns are imported into session documents before the index is published. Import is restartable until that publication. The old tables remain untouched and are never used as a second writable store. Pending legacy turns retain their frozen context and original per-request Pi job identity. The job snapshot/hash machinery in `agent.ts` remains for these legacy retries and the existing one-shot language endpoints; new study turns do not create job rows or per-request databases.

`studyResponse(run, errorMessage)` is an HTTP adapter: it sends NDJSON snapshots, heartbeats and completion while handling backpressure and cancellation. Disconnecting stops delivery, not the durable save. `readStudyStream<Session>` decodes the browser protocol and releases its reader. Neither implements agent scheduling or model streaming. Progress exposes only the top-level reply, keeping learner JSON and tool arguments out of the student-facing text. Routes own access checks, JSON compatibility and safe errors; subject pages own presentation.

History fixtures demonstrate a second learner schema and archive tool without shipping an additional subject. Tests also cover SQL import, native multi-turn context, request conflicts, retry/replay, failed-response discard, disconnect-safe saves and resource cleanup. An interrupted-session regression verifies that a second custom endpoint using the same model ID cannot receive the first session’s context. The old math exports, including `readMathStream`, remain aliases for existing consumers.
